# ADR-0015: IPv4 until v1.0, IPv6 as one family per deployment afterwards

- **Status:** Proposed
- **Date:** 2026-11-20
- **Deciders:** maintainers
- **Refines:** [ADR-0003](0003-scope-and-boundary.md) D4 (IPv6 among the network services in scope), [ADR-0004](0004-planes-and-isolation.md) (planes and admission)

## Context

ADR-0003 puts IPv6 among the network services of the scope of `v1.0`, and the design described it as dual stack on the planes and the tenant networks, with the same roles and admission rules for both families. Before designing it, the maintainers checked what the building blocks of the reference support (November 2026):

| Building block | IPv6 | Dual stack |
|---|---|---|
| Neutron | Tenant subnets (SLAAC, DHCPv6), routers and their routes. No NAT and no floating IP in IPv6, by design | Yes, two subnets on a network |
| Octavia | IPv6 VIPs | A VIP with an address of each family (`additional_vips`, API 2.26, Zed and later); limits on UDP and SCTP (Stream Control Transmission Protocol) listeners |
| OpenStack provider for OpenTofu and Terraform | IPv6 subnets (`ipv6_address_mode`, `ipv6_ra_mode`), IPv6 VIPs | No `additional_vips` on `openstack_lb_loadbalancer_v2`: a dual-stack load balancer takes two load balancers, one per family |
| OpenStack cloud controller manager | A Service of one family gets a load balancer of that family | A Service with both families gets one load balancer, of the first family only |
| Cluster API provider for OpenStack | IPv6 addresses of the machines in their status; ports with fixed IPs in both families | The API endpoint has a single address; whether the cluster is complete in dual stack is not established |
| Kubernetes, Cilium | IPv6 single stack supported | Dual stack stable since Kubernetes 1.23 |

Three more constraints come from outside these blocks:

- **No NAT in IPv6.** The planes provided by the operator with address translation (ADR-0004, D1, first case) have no IPv6 equivalent: in IPv6, operator planes are routed planes (address scopes, the third case). Exposure without floating IPs needs a public IPv6 prefix that the cloud routes to the VIP.
- **Metadata over IPv6.** An instance with IPv6 only reaches the metadata service at `fe80::a9fe:a9fe`, which depends on the Neutron metadata agent of the cloud; otherwise a configuration drive.
- **The IPv4 Internet.** Part of what the reference downloads is served over IPv4 only (GitHub, which hosts releases, `clusterctl` and charts). An IPv6-only deployment needs NAT64 and DNS64, which Neutron does not provide, or internal mirrors.

Most OpenStack clouds, private and public, offer tenants IPv4; some public clouds add IPv6 on their public network. Where IPv6 is required, as for the United States federal agencies (OMB M-21-07), the target is IPv6 only, internal networks included, not dual stack: running two families doubles the address plans, the firewall rules, the attack surface and the troubleshooting.

## Options considered

1. **Dual stack in an intermediate release before `v1.0`.** It touches the contracts of the planes, the admission rules, the entry point, both tenant types and the isolation test. The exposure takes two load balancers per address, a Kubernetes cluster would serve its ingress and its API in one family, and the cluster provider's support is not established. A breaking change near `v1.0`, for a partial result.
2. **Dual stack for the planes and the VM tenants only.** Feasible, but the entry point still needs two load balancers, and a reference whose Kubernetes tenant cannot follow is inconsistent.
3. **IPv4 until `v1.0`, then one family per deployment** (chosen). The reference stays IPv4 and says so. After `v1.0`, a deployment chooses IPv4 or IPv6, not both: one address plan, one set of rules, each block used in the single-stack mode it supports.
4. **Dual stack after `v1.0`.** Kept only for when the provider and the cloud controller support it (below).

## Decision

### D1 — IPv4 until v1.0

The reference creates no IPv6 subnet. Tenant instances get no IPv6 address beyond the link-local one (`fe80::/10`) that every interface configures by itself and that no router forwards: no routed IPv6 path exists between tenants, the planes or the Internet. The isolation stated by the matrix holds for IPv6 by absence. The planes contract says it: a plane, a tenant network and a shared service are IPv4.

### D2 — The absence is tested

The isolation test checks that no tenant instance has a global IPv6 address or an IPv6 default route. A cloud that adds IPv6 to the networks on its own, or a change that creates an IPv6 subnet, is detected, rather than leaving an unguarded path next to the IPv4 rules.

### D3 — After v1.0: one family per deployment

IPv6 comes back as a choice of family for the whole deployment, IPv4 or IPv6, when these hold:

- the cluster provider builds a complete cluster in IPv6 only: machines, its API load balancer, the cloud controller's Services;
- instances reach the metadata service over IPv6, or the stacks use a configuration drive;
- the tenants reach what they download without IPv4: the mirrors and registry of the network services, or NAT64 and DNS64 provided by the cloud.

In IPv6, the planes are hub planes or routed operator planes; exposure uses an IPv6 prefix routed by the cloud instead of floating IPs. The isolation test probes the addresses of the chosen family.

### D4 — Dual stack only on conditions

Dual stack is reconsidered when the OpenStack provider supports `additional_vips` and the cloud controller creates a load balancer per family, and when a user needs both families at once.

## Consequences

- The release order of the README no longer lists IPv6 before `v1.0`; it is listed after `v1.0`.
- The design (architecture, audiences, planes contract) describes the reference as IPv4, with IPv6 as a later choice of family.
- The row of D2 is added to the isolation test with the network services (`v0.6`), where the egress of the tenants is reviewed.
- When D3 starts, the inputs carry the family of the deployment; the contracts keep one range per plane and per attachment, in that family. The migration from IPv4 to IPv6 is a new deployment, not an in-place change.
